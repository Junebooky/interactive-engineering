## 1. Why the missing bridge matters
A student can know NAND, NVMe, GPU, memory and networking yet still imagine "SSD data travels through CPU arithmetic before RAM/GPU", "128 GT/s means 128 GB/s", "a four-level signal has 4 bits/transfer", or "all DMA devices can share any other device's memory." 29 fills the physical-vs-protocol/data-vs-addressing gap before Lesson 08 RDMA and Lesson10 one-AI-request lab.

## 2. Differential SerDes vs simple parallel wires
- Serial serializer/deserializer uses high-speed channel(s), clock recovery/retimer/equalization, not just "one copper line with zero latency". A PCIe **lane** has transmit and receive paths (full duplex); x4/x16 indicates lane count, not bytes per packet. Links negotiate link generation and lane width based on both endpoints/platform/routing/electrical quality.
- NRZ 2 voltage levels (rough abstraction), PAM4 **four amplitude levels encoding 2 bits per symbol**; PCIe6 **64.0 GT/s** and PCIe7 **128.0 GT/s** are *specification transfer-rate names* already used in FAQ bandwidth figures. **Do not apply another ×2** to the published 64/128 GT/s as though those units were independent symbol rates. Signal eye diagram can have 3 eyes for PAM4; pre/post-FEC bit error and power/latency tradeoffs, not automatic "PAM4 error-free". Distinguish GDDR7 PAM3 (3 levels not 3bits) from PCIe PAM4.

## 3. Public PCI-SIG bandwidth numbers / full duplex
- [PCI-SIG PCIe7 FAQ] `128.0 GT/s`, up to **512.0 GB/s full bidirectional aggregate at x16**. **Published link maximum**, not single direction/app payload/latency guarantee. For symmetrical math in the FAQ framing: one direction `512/2=256 GB/s`; x4 relative same generation `256*(4/16)=64 GB/s`; x1 `256/16=16 GB/s`. Each arithmetic result is **illustrative spec-envelope scaling**, not a benchmark.
- [PCI-SIG PCIe6 FAQ] `64.0 GT/s`, up to **256.0 GB/s full bidirectional aggregate x16**, so directional `128 GB/s` and theoretical x4 `32 GB/s`.
- Cross comparison for a **chosen 1GB decimal payload** purely ideal transfer lower bound `T=S/B` ignores FLIT framing, headers, FEC/CRC, link training, queue contention, DMA setup, device controller speed and software: at 32 GB/s `1/32=0.03125s=31.25ms`; at64 GB/s `15.625ms`. NOT actual time-to-first byte, not user SSD file transfer (which has other bottlenecks). Unit GB base10, don't treat GiB as GB. This exercise teaches throughput-vs-latency.
- Spec listing/release != all CPUs/GPUs/NVMe switches commercially implementing gen7 or gen6; card-endpoint fallback common in practice but no claim about which specific SKU. Link width may be negotiated lower.
- PCIe6 introduced **256-byte FLIT** (fixed; TLPs and DLLPs, FEC/CRC). Public PCI-SIG blog uses 236 bytes of TLP-carrying region in 256B flit → **236/256=0.921875 (92.1875%)** *TLP-carrying region fraction*, **not** payload bytes returned to an application: individual TLP headers/completion, DLLP, empty slot/padding and control overhead still matter; never multiply every real SSD data transfer by this factor to "predict" device throughput.
- PCIe7 also uses PAM4 and FLIT per official FAQ, but **do not imply its every TLP/FEC byte allocation equals PCIe6's illustrative 236/256** without original current standard section. This is explicit "unknown" in lesson.

## 4. CPU address vs device DMA address — correct arrows
- For ordinary Linux device DMA (single example): kernel/driver owns a buffer `CPU virtual X` → host page-table physical Y; DMA API `dma_map_single(dev, buffer, direction)` provides **device-visible DMA/bus address Z**, potentially translated by IOMMU from Z to Y. Three numbers may differ. No claim device can directly dereference arbitrary user virtual pointers; IOMMU protection/mapping and data ownership matter.
- Toy PCIe NVMe read: **host CPU/driver** submits NVMe read command (SQ entry in accessible host RAM, queue doorbell MMIO)→ controller obtains command/PRP/SGL and transfers payload **SSD controller → PCIe→ mapped host DDR buffer** by DMA; completion posted to CQ and host notified (interrupt/poll). Actual platform memory ordering, BARs/queues are additional stages. GPU transfer separate: host buffer→GPU VRAM by configured DMA; supported P2P/GPUDirect variant may avoid host staging **but not universally**. **NVMe protocol/PCIe link/NAND silicon/SSD controller/GPU VRAM are distinct layers.**
- Linux DMA_TO_DEVICE means **host main memory→device**, DMA_FROM_DEVICE means **device→host main memory**, not direction of application read/write command. For NVMe read payload from SSD to host RAM use DMA_FROM_DEVICE; for write payload host→SSD DMA_TO_DEVICE (from perspective of mapping device).
- DMA coherent mapping vs streaming mapping does **not** mean CPU ownership/dma memory ordering never matters; Linux documentation requires barriers and ownership/sync. IOMMU may translate and restrict device access, but its presence and isolation/permission effectiveness are system/platform/config dependent.
- **P2P**: Linux PCI P2P document states route via switches/ACS can remain within PCI hierarchy, but across host bridge/root ports routing not universally guaranteed; OS/driver may block unsupported topology; requires driver cooperation. Rendering all endpoints connected on a board as "SSD always direct to GPU" is a scientific error.

## 5. CXL: physical transport does not imply identical memory semantics
- Public CXL Consortium technical articles distinguish `CXL.io` config/registers/interrupts like PCIe, `CXL.cache` device access to coherent host memory, `CXL.mem` host access to device-attached memory (architecture and device types vary).
- CXL uses PCIe-derived physical infrastructure and memory/coherency protocols. **CXL.mem link is not an SSD NVMe queue** and is not equivalent to direct local DDR latency just because it is memory-addressed. A CXL Type-3 memory expansion is different from HBM attached GPU and requires host/platform/OS/NUMA placement support. Memory pooling/tiering can improve capacity but may degrade latency-sensitive hot accesses; no fixed performance guarantee.
- Public **CXL Consortium 2025-11-18 announcement** says CXL4 doubles spec link rate from64 to128GT/s, adds bundled ports and memory RAS features. Its phrase *"zero added latency"* refers to that speedup/protocol-generation claim, **not literal zero end-to-end remote-memory latency**; leave performance under NEEDS MEASURE.
- **CXL evaluation specification is license-restricted, includes explicit AI processing restrictions** (current consortium download agreement observed on public page). Do NOT fetch/process/reproduce/download it. Cite publicly released consortium blogs and announcement summary only.
