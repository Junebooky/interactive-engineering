## 21-S01 · KV cache math, MHA/GQA, dimensions and units
- Causal need: autoregressive decode computes new token queries and can reuse previously computed key/value tensors across layers; saved KV grows with cached token count. For a **full-attention** decoder with uniform per-layer heads, ideal unpadded KV bytes/token = `2 (K and V) × numLayers × kvHeads × headDim × bytesPerElement`. Query heads can be more numerous than **KV heads** in grouped-query attention GQA, but KV allocation follows KV heads, not query heads; NVIDIA TensorRT-LLM and Hugging Face docs differentiate model-specific MQA/GQA and attention window [R1,R2,R3].
- Toy `numLayers=16`, `queryHeads=16 fixed`, `kvHeads=4|8`, `headDim=64`, `precisionBytes=2` FP16, `cachedTokens=128|256`. For kv4: 2×16×4×64×2=16,384 bytes/token=16KiB/token, at128=2,097,152 bytes=2MiB and at256=4MiB. kv8:32KiB/token,128=>4MiB and256=>8MiB. Holding queryHeads16 fixed does not imply all models use kvHeads4. Real activations, alignment/allocator, block padding, multi-modal features, sliding windows and prefix blocks add other costs; this formula not total GPU use.
- Wrong state: `queryHeads=16` substituted for actual kvHeads4 and inflated by4×; tokens count without layers; 2MiB KV ≠ 2MB decimal (1MiB=1,048,576 bytes); KV optimization does not erase GPU weight memory.

## 21-S02 · PagedAttention maps variable-length requests into token blocks
- vLLM PagedAttention paper 2023 [R4] and vLLM official design [R5,R6] partition KV cache into fixed token blocks and use a mapping to non-contiguous physical blocks, allowing on-demand allocation and block sharing. *Internal fragmentation* is still possible inside each request's last block; paged does not imply zero memory waste; allocator bookkeeping and physical memory overhead remain.
- Classroom independent `blockTokens=16 fixed`, `requestA_length=17|31`, `requestB_length=17|31`; allocated capacity sum `16*ceil(LA/16)+16*ceil(LB/16)`. For A17+B31 ⇒2blocks each⇒64 token slots allocated,48 token positions actually used,16 unused =25% allocation; for A31+B31⇒64 slots/62 used=>2 unused=3.125%; for A17+B17⇒64 slots/34 used=>30 unused=46.875%. Distinguish `usedTokens` from real bytes/head/layer footprint; chosen 16-token block simplified; actual vLLM config and hybrid layers different, no GPU throughput guarantees.
- Fixed contiguous *toy alternative* always reserves64 token slots **per request**, so two requests reserve128 slots vs paged64 for 17/31. This is NOT the original PagedAttention paper baseline measurement (benchmark workloads/perf and reference allocator differ), just fragmentation illustration. On-demand allocation can affect batching capacity but cannot assert 2–4× throughput universal. Vendor/paper cited evaluations only conditional and historical.

## 21-S03 · KV precision, quantization error and backend status
- Hugging Face Transformers current docs [R2] describe QuantizedCache with e.g. HQQ int2/int4/int8 and Quanto int2/int4, per-backend runtime/version caveat. Lower-bit KV can reduce memory but scale/zero-point/residual FP data and kernel overhead consume nonzero memory; short contexts may run slower; low-precision error can affect model quality. Model weight quantization and **KV state quantization** are separate datasets and cost/accuracy axes.
- Under exact toy KV from S01 kvHeads4: FP16 2MiB/128 tokens; ideal INT8 payload half=1MiB/128 tokens, **without metadata**; at 256 tokens FP16 4MiB, INT8 2MiB. Precision choice int8 in this scene is **hypothetical arithmetic**, not a promise a given Hugging Face QuantizedCache backend/version offers int8 or current kernel yields speedup. Quantization arithmetic for *scalar toy* `q = round(x/scale)` and dequant `xhat=q*scale`; independent inputs `x=0.26|0.34`, `scale=0.10|0.20` giving (0.26,.1)⇒q3,xhat.30,error+.04, (0.26,.2)⇒q1,xhat.20,error−.06, (.34,.1)⇒q3,xhat.30,error−.04, (.34,.2)⇒q2,xhat.40,error+.06. No ties. Real per-channel grouping, clipping/overflow, calibration, softmax sensitivity, task accuracy and attention kernels excluded.
- Grossly wrong: `INT8 payload half`→overall GPU memory half; lower bits always faster; one scalar reconstruction error proves model factual truth. State `actualQuality=NOT_PROVEN`, `actualThroughput=NOT_PROVEN`, `metadataOverhead=UNKNOWN` at all times.

## 21-S04 · GPU/CPU KV offload changes capacity and transfer costs, not magic throughput
- HF [R2] documents offloading KV tensors of selected layers to CPU while currently processed layer remains on GPU; latency can decrease under GPU capacity pressure yet transfer/PCIe costs can increase. NVIDIA [R3] block manager includes prioritized eviction/offload; precise semantics and version matter. This lesson's **simplified whole-request-tier** allocation is NOT the Hugging Face algorithm (documented separately), no specific API guarantee.
- Fictional GPU memory budget8MiB, unrelated weights+system reservation4MiB, thus cache capacity4MiB; each toy request's KV footprint2MiB. With no offload, at most2 request caches fit in GPU toy. If one existing 2MiB KV cache moved to CPU and a **different request** allocated in freed GPU slot, on-GPU2 plus CPU1 ⇒3 cached request states across both tiers, but not 3 GPU-resident simultaneous attend steps and does not prove throughput growth. `offloadEnabled` independent of `linkGiBPerSecond=1|2`. A one-way2MiB transfer at 1GiB/s ideally `2/1024s=0.001953125s=1.953125ms`; at 2GiB/s =>0.9765625ms. *Serialization lower bound only*, actual latency higher with protocol, DMA, contention, per-layer multiple transfers, scheduling and CPU capacity.
- Bad inference: Offload frees weights or raises arithmetic TOPS; one-way transfer bound equals TTFT or guaranteed total decode latency; offload returns more on-GPU-only simultaneous requests. If no offload selected transfer time0 in toy, CPU-cached requests0.

## 21-S05 · Prefix caching work reuse, cache-salt identity and tenant isolation
- vLLM v1 prefix caching [R5] hashes full KV blocks based on parent prefix, token content and optional model/adaptor/multimodal/salt; note **only full blocks cached** under that design and refcounts/eviction matter. Official vLLM security guidance [R7] explicitly says **shared server process does not isolate tenants**, and `cache_salt` reduces some timing/side-channel risks but **is not a security boundary**. Dedicated vLLM instances per tenant or authenticated gateway/scope are relevant alternatives. Do not imply cache salt alone can replace authentication or prevent side-channel risk universally.
- Toy two requests, 48 tokens each with distinct suffix and identical declared first `sharedPrefixTokens=16|32`, `blockSize=16`, **precondition actual token-prefix match verified**. Without reuse: 96 abstract *prefill token-equivalent* computations. With same **authorized tenant**, same secret-scoped salt, matching full blocks and no eviction: shared 16⇒new work96−16=80; shared32⇒64. This is **work units not TTFT, real GPU FLOPs or tokens/s**. If different tenant (or salt mismatch), `CROSS_TENANT_POLICY_DENY` / `SALT_MISMATCH_NO_REUSE`, work96; direct same salt with different tenant is STILL denied by application policy (salting not a hardened isolation boundary). `tenantSame:boolean` and `cacheSaltMatches:boolean` are independently typed controls (not actual secrets), `prefixTokens=16|32` choice, `authorizedReuse` requires same tenant+salt+true identical full prefix. Real tokens/LoRA ids/hashes not used; never expose private prompts between users.
- Bad inference: shorter TTFT always means leaked cache content; cache_salt is strong trust boundary; changing tenant after retrieval retroactively makes a previously served prefix authorized; a prefix match not verified by token IDs can safely reuse; full block only vs partial block.
