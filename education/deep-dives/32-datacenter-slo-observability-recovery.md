## End-to-end request spans, measurement boundaries
- OpenTelemetry's trace/span model uses trace id + span ids, start/end time, parent relation, events and attributes [C1]. The total request wall-clock duration is root span end-start (under correct time sync/context propagation), **NOT sum of nested or parallel child-span durations**. Actual distributed clocks can skew, incomplete spans or sampling can omit critical work; hardware instrumentation and trace context need checking.
- Synthetic chronological toy: gateway 0–20ms, tokenizer 20–30ms, GPU generation 30–110ms, response send 110–120ms. Root request0–120ms =120ms. Side logging span30–60ms runs in parallel with GPU; sum of five individual span lengths including logging =20+10+80+10+30=150ms, but root wall time120ms. Optional cold model-loading stage30–70ms before GPU (GPU70–150ms), response150–160ms =>160ms root, not same request repeated SSD read on every token. A source-level lesson must disallow double counting child time and missing request deadline.

## Success SLI, SLO, burn versus p99
- Google SRE [C2/C3] uses SLI numerator/denominator and documented eligible populations/windows; error budget ratio = 1−SLO. Toy 1000 eligible requests in one fixed window, availability SLO 99.9% means max1 bad if equal request weights. 990 successful+10 unsuccessful gives observed99.0%; observed error fraction1% /allowed0.1% =10× normalized **burn rate** under equal elapsed measurement window and request sample, and **10× allowed errors** for same 1000 requests. Excess failures9. This is **not** tenfold every real alert window unless period/traffic normalization agrees; percentile tail measurement is a separate SLI.
- Error classification should be user-visible and specified before experiment. Dropping timeouts from denominator is not a legitimate metric improvement; sampling can bias service conclusions. SLO!=SLA legal penalty, p99!=99.9% availability, PUE!=application goodput.

## Overload and retry feedback
- Google SRE [C4] cautions that retries (without backoff/jitter/budget) can amplify load and cause cascading failure; load shedding and exponential backoff have tradeoffs. Toy server capacity=5 requests/tick, baseline new requests4/tick, two initial failed each tick under an illustrative fault. Without retries, arriving4 ≤service5; immediate-once retry in next tick adds2⇒6 arrivals, queue increases by1/tick if no drop; spreading fixed two retried requests as one each over two slots yields5 arrivals/tick at capacity assuming no new retries generated. **Toy intentionally freezes the retry cohort**; it does not realistically model recursive failures, deadlines, fairness, health or a real 503/error-budget effect. Backoff doesn't resurrect down hardware; client retries can worsen user p99.
- Choose retry limits/timeouts, cap max attempts, idempotency, dedupe/circuit breaker, and load shedding (with honest rejected-request SLI). No blanket 'retries always improve availability' assumption.

## RTO vs RPO, tested backup restore
- AWS Well-Architected [C5] defines RTO maximum acceptable time between interruption and restoration, RPO maximum acceptable lookback from data-recovery point to outage; they are distinct **targets**, while achieved downtime/data-gap are measured on restore. Synthetic clock: outage t=60min, last verified durable checkpoint t=50min, live healthy after restore t=68min: observed restore downtime8min, *potential* uncheckpointed gap10min. With target RTO≤10min PASS, RPO≤5min FAIL. If checkpoint t58min **and independently verified restorable**, RPO gap2min PASS. If `restoreValid=false`, backup existence alone yields NO_PROVEN_RECOVERY even if checkpoint timestamp appears recent.
- Storage replica, checkpoint consistency, metadata/PLP completion, replay and client session recovery must be modeled separately; CPU/GPU/NVMe healthy != user service recovered. Published backup strategy without actual recovery test is insufficient [C6].

## Facility energy vs tokens/requests and site water
- US DOE/FEMP [C7] PUE facility energy / IT energy same boundary/time; WUE site water liters / IT equipment kWh. Fictional identical **IT 1MW average for one hour** yields1000kWh IT energy. B lower PUE efficiency score (PUE1.4 >1.2) but better fictional business goodput/facility energy and site WUE. **This does not imply B higher model answer quality, latency p99, carbon benefit, or real site sustainability.** Keep workload/response quality and measurement boundaries clear.
- Facility cooling-water recirculation per second **is not** annual site water use; material not enough to infer WUE or carbon intensity, time/location/energy mix matters. Product/TCO recommendations require metered operation, not toy.
